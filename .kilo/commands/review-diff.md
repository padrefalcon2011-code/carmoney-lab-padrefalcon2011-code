# Ревью изменений перед мержем

Использование: `/review-diff <файл|ветка>`.

Параметр задаёт единственную область ревью:

- путь к файлу — проверь только изменения и код этого файла;
- имя ветки — проверь diff текущей ветки относительно указанной ветки.

Если параметр не передан, не начинай ревью и попроси пользователя указать путь к файлу или
имя базовой ветки.

1. Определи область ревью только из переданного параметра.
2. Изучи изменения в этой области: для файла — его незакоммиченный diff и различия текущей
   ветки с базовой веткой; для ветки — diff текущей ветки относительно переданной ветки.
3. Для поиска определений, использований и связей в коде следуй скиллу
   [`ast-index-workflow`](../skills/ast-index-workflow/SKILL.md). Не дублируй его инструкции.
4. Проверь изменения на ошибки, регрессии, риски безопасности и отсутствие нужных тестов.
5. Проверь только переданную область и её непосредственные зависимости.

## Чего не делать

Не изменяй файлы, не запускай необязательные полные тестовые наборы, не расширяй ревью за
переданный файл или ветку и её непосредственные зависимости и не создавай коммиты или PR.

## Формат результата

Верни только ревью в Markdown по этому шаблону с точными заголовками; не добавляй текст до,
после или вне этих разделов:

```markdown
## Findings

- Область: `<переданный файл или ветка>`.
- `severity` — `path:line`: проблема, влияние и рекомендуемое исправление.

## Open Questions

- Вопрос или `Нет`.

## Summary

- Краткий вывод о готовности изменений к мержу.
```

Сначала перечисли findings по убыванию серьёзности. Если проблем нет, явно напиши
`Нет findings` в соответствующем разделе. Даже если в переданной области нет diff, верни все
три раздела формата результата: в `Findings` укажи область и `Нет findings`, в `Open Questions`
укажи `Нет`, в `Summary` объясни, что изменения для ревью отсутствуют. Результат в файл не
сохраняй: верни его в ответе текущей сессии.
